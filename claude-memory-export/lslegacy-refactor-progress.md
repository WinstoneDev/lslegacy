## LOT 3 — détail (faille de sécurité corrigée)
- **`module/bank/sv_bank.lua` `BankAddMoney`** (event serveur déclenché par le client) : AUCUNE validation d'amount, contrairement à `BankwithdrawMoney`/`BankTransferByIban` qui en ont une. Un `amount` négatif faisait `RemovePlayerMoney(player, amount)` → `cash - (-x) = cash + x` (le joueur GAGNE du cash) tout en débitant le compte bancaire du même montant négatif (donc le bank AUGMENTE aussi côté compte... en fait `account.amountMoney + amount` avec amount négatif décrémente le compte) → duplication d'argent nette. Corrigé avec `LSLegacy.Validate.PositiveInteger` + `LSLegacy.Validate.Player`.
- **`server/player/money.lua`** (Core) : `SetPlayerMoney`/`AddPlayerMoney`/`SetPlayerDirtyMoney`/`AddPlayerDirtyMoney` n'avaient AUCUNE validation. `RemovePlayerMoney`/`RemovePlayerDirtyMoney` comparaient `player.cash >= tonumber(amount)` : plantait (erreur Lua "compare number with nil") si amount non numérique, et laissait passer les négatifs (même exploit que BankAddMoney). Les 6 fonctions utilisent maintenant `LSLegacy.Validate.PositiveInteger` (Set* avec `allowZero=true`) et renvoient `true`/`false`.
- **`server/boutique.lua` `AddCredits`** : plantait si le montant Tebex n'était pas numérique (`nil <= number`). Corrigé avec `LSLegacy.Validate.PositiveInteger`. Risque plus faible (appelé uniquement depuis la commande console `addcredits`, `source == 0`), corrigé par cohérence/robustesse.
- Vérifié `BankwithdrawMoney`, `BankTransferByIban`, `BankDepositLivret`, `BankWithdrawLivret` : déjà correctement validés (pattern `tonumber(amount) or 0` + `<= 0 then return`), non touchés.

- **`giveItem` (event serveur déclenché par le client via le dispatcher générique `useEvent`)** : branche `item == 'money' or item == 'dirty'` supprimée — elle appelait `AddPlayerMoney`/`AddPlayerDirtyMoney` avec un `quantity` 100% contrôlé par le client, sans aucune vérification de légitimité (argent gratuit illimité). ## LOT 6 — détail (DataStore security, server/datastore.lua + inventory/server/main.lua)
Mécanisme d'accès existant découvert : `LSLegacy.DataStoreGuard(src, name, action, item)`, fail-open par défaut (`return true`), chaîné par les modules via `local prevGuard = LSLegacy.DataStoreGuard; LSLegacy.DataStoreGuard = function(...) ... if prevGuard then return prevGuard(...) end end` (déjà utilisé correctement par `module/keyhanger` et `module/atelier`, qui `return false` explicitement pour leurs propres préfixes sur les events génériques). Ce pattern de chaînage EST le mécanisme générique demandé — pas besoin de le remplacer, juste de combler les trous non couverts par un module :
- **Faille critique — `RegisterDataStore` (event réseau, `server/datastore.lua`)** : any client pouvait créer un DataStore avec `money`/`dirty`/`inventory` arbitraires (le client `LSLegacy.DataStore.RegisterDataStore` normal envoie toujours du contenu vide — `client/datastore.lua` — mais rien ne forçait ça côté serveur). Combiné au guard fail-open, un joueur pouvait créer un stash privé pré-rempli d'argent/objets et le vider avec `TakeFromTrunk`. Corrigé : le handler réseau force désormais `inventory={}, money=0, dirty=0` côté serveur quoi que le client envoie ; seul `type`/`maxWeight` (validé `PositiveInteger`) sont repris.
- **Coffres/vide-poches véhicule (`trunk_<plaque>`/`bag_<plaque>`) sans aucune règle** : ni distance, ni vérification qu'un véhicule avec cette plaque existe réellement — la plaque est visible/devinable, donc n'importe qui pouvait vider/remplir n'importe quel coffre à distance. Ajout d'une règle Core dans `inventory/server/main.lua` (chaînée avant `prevGuard`, donc n'affecte pas keyhanger/atelier qui ont leurs propres préfixes) : exige un véhicule réel portant cette plaque à ≤5m de la source.
- **`PutIntoTrunk`/`TakeFromTrunk` (`item_standard`)** : `data.uniqueId`/`data.data` (transmis par le client) remplacés par les valeurs authentiques lues côté serveur (`GetInventoryItem` sur l'inventaire joueur ou le datastore) — même faille de spoofing d'item unique que LOT 4 (transfer), même fix.
- **`LSLegacy.DataStore.AddMoney/RemoveMoney/AddDirtyMoney/RemoveDirtyMoney`** : aucune validation d'`amount` (contrairement à `LSLegacy.Money.*` depuis LOT 3). Un `data.count` négatif dans `PutIntoTrunk`/`TakeFromTrunk` permettait de gonfler l'argent d'un datastore sans coût réel (les fonctions joueur validées en LOT 3 échouaient silencieusement sur le montant négatif, mais le côté datastore, non validé, s'exécutait quand même) — argent créé dans un stash partagé, retirable ensuite normalement = duplication. Corrigé avec `LSLegacy.Validate.PositiveInteger`, renvoient maintenant `true`/`false` (aucun appelant existant n'inspecte la valeur de retour, vérifié).
- **`LSLegacy.DataStore.AddItemInInventory/RemoveItemInInventory`** : même trou de validation de `quantity` que LOT 4 (player inventory), même fix (`PositiveInteger`).
- Non touché : la logique métier propre à `atelier`/`keyhanger` (déjà correctement gardée), pas de nouveau système déclaratif de règles créé — le chaînage `prevGuard` existant suffisait et reste la convention pour les futurs modules.

## LOT 7 — détail (callbacks ESX résiduels, server/callbacks.lua + client/callbacks.lua)
- Bug réel trouvé (pas juste cosmétique) : le système de callbacks bidirectionnel était totalement cassé. Le serveur envoyait `TriggerClientEvent("esx:triggerClientCallback"/"esx:serverCallback", ...)` mais le client n'écoutait que sur les noms sans préfixe (`triggerClientCallback`/`serverCallback`, enregistrés via `LSLegacy.RegisterClientEvent`) ; symétriquement le client envoyait `TriggerServerEvent("esx:triggerServerCallback"/"esx:clientCallback", ...)` en brut (hors dispatcher `useEvent`) alors que le serveur les attend via `LSLegacy.RegisterServerEvent` (donc uniquement dispatchables via `useEvent` + jeton). Résultat : `AwaitServerCallback`/`AwaitClientCallback` ne recevaient jamais de réponse, timeout systématique au bout de 15s. Confirmé par les commentaires déjà présents dans `module/pompe/server/main.lua` et `module/mdt/*` documentant ce contournement (event-driven au lieu d'callback).
- Fix : les 4 appels réseau remplacés par `LSLegacy.SendEventToClient`/`LSLegacy.SendEventToServer` (transport standard du Core, avec jetons anti-injector côté client→serveur), en gardant exactement les mêmes noms d'event que ceux déjà enregistrés côté récepteur (`triggerClientCallback`, `serverCallback`, `triggerServerCallback`, `clientCallback`) — plus aucune référence à `esx:`.
- API propre ajoutée par-dessus, sans rien casser : `LSLegacy.Callbacks.{RegisterServer, TriggerClient, AwaitClient}` (serveur) et `LSLegacy.Callbacks.{RegisterClient, TriggerServer, AwaitServer}` (client) — simples alias vers les fonctions existantes (`LSLegacy.RegisterServerCallback`, etc.), qui restent inchangées et continuent de fonctionner pour les modules déjà écrits avec l'ancien nommage (ex. `module/garage`).
- Commentaires obsolètes corrigés dans `module/pompe/server/main.lua`, `module/mdt/server/main.lua`, `module/mdt/client/main.lua` (ils affirmaient à tort que le système de callbacks n'était pas câblé).
- Pas touché : `shared/sv_config.lua` (listes `esx_*`/`esx:*` dans `Shared.Anticheat.BlacklistWords`) — ce sont des noms d'events tiers à détecter/bannir (anti-injecteur), pas une dépendance du Core à ESX, donc hors scope.
